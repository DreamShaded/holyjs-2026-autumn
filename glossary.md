# ML своими руками на JS

Словарь терминов доклада и разбор числа параметров модели design-dealer. HolyJS 2026 Autumn, Роман Троицкий. Версия от 13.10.2026.

Термины идут в порядке актов доклада. Для каждого дана метафора со слайдов, если она там была. Числа взяты из доклада и из репозитория design-dealer, часть формулировок — из словаря проекта `docs/glossary.md`.

## Часть 1. Словарь терминов

### Задача и данные

| Термин | Что это значит |
|---|---|
| Скриншотный тест | Тест снимает компонент, сравнивает снимок с эталоном и падает, если картинки заметно различаются. Отвечает на вопрос «где», но не «что именно». |
| Эталон (Expected) и рендер (Actual) | Эталон: снимок «как надо». Рендер: снимок «как стало», в тесте или после мутации. |
| Дифф | Результат сравнения двух картинок: какие пиксели не совпали. На первом слайде это красная заливка. |
| Маска диффа | Картинка того же размера, где у каждого пикселя отмечено, отличается он или нет. Это седьмой канал на входе сети: подсказка «смотри сюда». |
| pixelmatch, pngjs | pixelmatch сравнивает две картинки попиксельно и строит дифф. pngjs читает и записывает PNG. |
| Область отличий (bbox) | Самый тесный прямоугольник вокруг пятна отличий. Красная рамка на слайде «Что видит сеть», вокруг неё режутся окна. |
| Storybook, story | Storybook: витрина, где каждый компонент показан отдельно. Story: один компонент в одном состоянии, например `button--primary`. |
| Мутация | Программа нарочно меняет одно или два CSS-свойства перед вторым снимком. Правильный ответ известен заранее, руками ничего размечать не нужно. |
| Пара | Эталон и рендер одного компонента с известной мутацией. Единица датасета. |
| Метка | Правильный ответ для примера: какие свойства сломаны. |
| Датасет | Набор пар с метками. В финальном прогоне: 4022 пары и 72 469 окон. |
| Окно 64×64 | Квадрат, вырезанный вокруг области отличий в натуральном размере, без растягивания и сжатия. В докладе: «лупа». |
| Перекрытие окон | Соседние окна заходят друг на друга на 16 пикселей (шаг 48), чтобы буква на границе целиком попала хотя бы в одно окно. |
| Голосование окон | Сеть отвечает по каждому окну, ответы окон одной области отличий усредняются. В обучение с одной пары берётся не больше 16 окон (флаг `--max-windows-per-pair`), иначе данные не влезают в память вкладки. |
| Пропущенные пары | `skippedEmptyDiff`: свойство изменили, а ни один пиксель не поменялся. `skippedInvisibleMutation`: при двойной поломке одну из двух не видно отдельно. Такие пары выбрасываются, а не идут в обучение с неверной меткой. |
| Находка | Результат для упавшего теста: story, область отличий, свойство и уверенность сети. Пример: `button--primary: область 12,40–180,72: color (0.94), font-weight (0.71)`. |
| Свойства | Пять CSS-свойств, которые различает сеть: `color`, `font-weight`, `letter-spacing`, `line-height`, `border`. |
| Реестр свойств | Единственный список свойств вместе с правилами их мутации (`src/registry/properties.ts`). Из него берутся число выходов сети и порядок лампочек. |
| design-dealer | Проект из доклада: маленькая свёрточная сеть на TensorFlow.js, которая называет, какое CSS-свойство разошлось между эталоном и рендером. |

### Как устроена сеть

| Термин | Что это значит |
|---|---|
| Нейросеть | Функция с большим количеством настраиваемых чисел. Числа подбираются по примерам, а не записываются правилами «если — то». В докладе: «ручки-регуляторы». |
| Параметры (веса) | Те самые числа, которые меняются при обучении. У design-dealer их 97 653, подробности во второй части. |
| Признак | Свойство картинки, по которому сеть принимает решение: толщина штриха, расстояние между буквами. Признаки никто не пишет руками, их подбирает обучение. |
| Свёрточная сеть (CNN) | Сеть из слоёв свёрток. Подходит для картинок, потому что ищет локальные узоры в любом месте изображения. |
| Свёртка | Маленький фильтр весов 3×3 скользит по картинке. В каждой точке он умножает соседние пиксели на свои веса и складывает: получается одно число «насколько это место похоже на мой узор». В докладе: «трафарет». |
| Фильтр (ядро) | Набор весов одной свёртки: 3×3 на каждый входной канал плюс одно смещение. Один и тот же фильтр прикладывается ко всем местам картинки, поэтому палочку он находит и в «Т», и в «Г». |
| Слой («этаж») | Ступень сети. Нижние слои ищут штрихи и уголки, следующие складывают из них буквы и линии рамки, верхние замечают, что буквы или строки разъехались. |
| Рецептивное поле | Сколько исходных пикселей видит одна точка верхнего слоя. Растёт с каждым слоем и с каждым уменьшением картинки. |
| Max pooling | Уменьшение картинки вдвое: из каждого квадрата 2×2 остаётся максимум. В докладе: «отойти от картины на шаг». |
| Global average pooling | В конце каждый фильтр усредняется по всему окну до одного числа: «нашёл я своё где-нибудь или нет». Координаты пропадают, и они не нужны: место ошибки уже назвал pixelmatch. |
| Полносвязный слой (dense) | Слой, где каждый выход связан с каждым входом. У нас первый dense на 64 нейрона собирает ответы фильтров, второй выдаёт пять лампочек. |
| softmax | Делит 100 % уверенности между вариантами, в сумме всегда 100 %. Подходит, когда верный ответ ровно один. В докладе: «переключатель на стиральной машине». |
| sigmoid | Превращает каждый выход в число от 0 до 1 независимо от остальных. В докладе: «лампочки». |
| Multi-label | Задача, где верных ответов может быть несколько сразу: сломались и цвет, и жирность. |
| Порог | Правило «уверенность выше порога — считаем найденным». Это наша договорённость, а не часть сети. По умолчанию 0.5. Порог 0.3: 85 % двойных поломок названы целиком и 30 % ложных вторых свойств. Порог 0.5: 69 % и 12 %. |
| Тензор | Многомерная таблица чисел, с которой работает TensorFlow.js. Вход сети: 64×64×7. |
| Канал | Одно число на пиксель в тензоре. У нас семь каналов: RGB эталона, RGB рендера и маска диффа. В докладе: «три плёнки». |
| Трансформер (ViT) | Архитектура больших моделей для картинок. Без большого предобучения уступает маленькой CNN на нашей задаче и заметно тяжелее в браузере и Node. |
| MobileNet | Готовая предобученная CNN для распознавания объектов. Требует сжимать картинку до 224×224, а при сжатии теряются тонкие штрихи. |
| Предобучение | Обучение модели на большом чужом наборе данных до того, как её доучивают под свою задачу. |

### Как сеть учится

| Термин | Что это значит |
|---|---|
| Обучение | Многократный показ примеров с ответами. После каждой подсказки сеть немного подкручивает веса в сторону меньшей ошибки. |
| Loss (функция потерь) | Число «насколько сеть ошиблась». В докладе: «горячо — холодно». Loss меняется плавно от любого изменения уверенности, поэтому всегда подсказывает, в какую сторону крутить веса. |
| binaryCrossentropy | Loss для лампочек: каждая лампочка получает свой штраф как ответ «да или нет». |
| Обратный проход | Расчёт того, как изменить каждый вес, чтобы loss уменьшился. Без него учить нельзя. У wasm-бэкенда TensorFlow.js обратного прохода свёртки нет. |
| Эпоха | Один проход по всем обучающим примерам. В докладе: «прочитать учебник от корки до корки». |
| Переобучение (overfitting) | Сеть запоминает конкретные примеры вместо общего правила и ошибается на новых. В докладе: «зубрёжка». |
| Отложенная выборка (validation) | Часть данных, которую сеть не видит на обучении. Оцениваем только на ней. В докладе: «контрольная». |
| k-fold, фолд | Story делятся на k кучек (фолдов), варианты одной story всегда в одной кучке. Сеть k раз учится на k−1 кучках и проверяется на оставшейся. У нас k = 5. Результат: среднее и разброс по всем прогонам. |
| Ранняя остановка (early stopping) | После каждой эпохи сеть пишет контрольную. Если оценка не улучшается несколько эпох подряд, обучение останавливается и берётся лучшая версия. |
| Patience (терпение) | Сколько эпох без улучшения ждём до остановки. У нас 3. |
| valLoss | Loss на отложенной выборке. Может расти, пока доля правильных ответов растёт: loss сильно штрафует уверенные ошибки. |
| Критерий остановки | Оценка, по которой решаем, что стало лучше. Сначала был valLoss, потом top-1 по парам (`stopMetric=top1pair`). Результат: 81 % → 85 % и 89 % в двух повторах. |
| Шум запуска | Разброс результата между одинаковыми запусками из-за случайных начальных весов. У нас около 4 пунктов. Разницу меньше шума считаем «не отличить». |
| Dropout | На обучении случайно выключается часть нейронов. Число параметров не меняется. |
| L2-регуляризация | Добавка к loss за слишком большие веса. Число параметров не меняется. Dropout вместе с L2 дали −8 пунктов: проблема была в данных, а не в сети. |
| Разнообразие данных | Было 12 story: шесть компонентов по два состояния. Стало 54: каждому компоненту добавили состояние (18 базовых story), к каждой — по два варианта со шрифтом Inter, Roboto или Lora, светлым или тёмным фоном и базовым размером текста 16 или 18 px. Среднее почти не изменилось (около 90 %), разброс между фолдами стал втрое меньше, на незнакомом Vuetify точность выросла с 47 до 81 %. |
| Утечка данных (leakage) | Варианты одной story попали и в обучение, и в проверку. Сеть узнаёт знакомую вёрстку, оценка завышена. Поэтому кучки собираются по базовой story: все её варианты всегда вместе. |
| Итоговая (шестая) модель | Учится на всех пяти фолдах сразу и идёт работать в тесты. Число эпох берётся из пяти проверочных прогонов: медиана лучших эпох 4, 6, 6, 9, 10 равна 6. |
| Медиана | Середина упорядоченного ряда. В отличие от среднего, почти не сдвигается от одного выброса. |

### Метрики

| Термин | Что это значит |
|---|---|
| Top-1 | Доля случаев, где самая яркая лампочка указывает на сломанное свойство. Случайное угадывание даёт 20 % (одна из пяти). |
| Top-1 по парам и по окнам | По парам каждый сломанный компонент голосует один раз. По окнам голосует каждое окно, и большие компоненты перевешивают. На Vuetify: 78 % по окнам против 53 % по парам. |
| Precision (точность) | Доля верных среди названных. В докладе: «сколько в улове рыбы, а не ботинок». |
| Recall (полнота) | Доля найденных среди реально сломанных. В докладе: «сколько рыбы из озера поймали». |
| Precision и recall вместе | Порог работает как размер ячейки сети. Ниже порог: recall растёт, precision падает. Пример из жизни: спам-фильтр. |
| Среднее ± разброс | Итог k-fold записывается как 80 ± 16 %: среднее по фолдам и то, насколько они расходятся. |

## Часть 2. Откуда 97 653 параметра

### Коротко

Число параметров никто не задаёт напрямую. Оно следует из архитектуры: размера входа, числа фильтров в каждой свёртке, ширины полносвязного слоя и числа выходов. Архитектура записана литералами в одной функции, `buildModel` в `src/model/arch.ts`. Отдельного конфига, переменных окружения или флагов CLI для ширины сети нет. 97 653 получается и по формуле, и по манифесту весов в `models/tier1/model.json`, и по размеру `weights.bin`: 390 612 байт ÷ 4 байта на число.

### Как считается

Каждый слой с весами вносит свою долю:

- свёртка: размер ядра × размер ядра × входные каналы × фильтры + по одному смещению на фильтр;
- полносвязный слой: входы × выходы + по одному смещению на выход;
- max pooling и global average pooling весов не имеют, они только уменьшают картинку.

| Слой | Каналы / форма | Формула | Параметры |
|---|---|---|---|
| conv1 | 7 → 16 | 3·3·7·16 + 16 | 1 024 |
| conv2 | 16 → 16 | 3·3·16·16 + 16 | 2 320 |
| max pooling | ÷2 | нет весов | 0 |
| conv3 | 16 → 32 | 3·3·16·32 + 32 | 4 640 |
| conv4 | 32 → 32 | 3·3·32·32 + 32 | 9 248 |
| max pooling | ÷2 | нет весов | 0 |
| conv5 | 32 → 64 | 3·3·32·64 + 64 | 18 496 |
| conv6 | 64 → 96 | 3·3·64·96 + 96 | 55 392 |
| global average pooling | 64×64×96 → 96 | нет весов | 0 |
| dense1 | 96 → 64 | 96·64 + 64 | 6 208 |
| dense2 (выход, sigmoid) | 64 → 5 | 64·5 + 5 | 325 |
| **Итого** |  |  | **97 653** |

Больше половины параметров (55 392, около 57 %) приходится на последнюю свёртку 64 → 96. Если сеть понадобится облегчить, начинать стоит с неё.

### Что влияет на число, а что нет

- **Число фильтров** влияет сильнее всего. Вклад свёртки пропорционален произведению входных и выходных каналов. Если удвоить оба, слой вырастет примерно вчетверо, вся сеть примерно втрое.
- **Число входных каналов** (7) влияет только на первую свёртку. Ещё один канал добавил бы 3·3·16 = 144 параметра.
- **Размер ядра** (3×3) входит в каждую свёртку квадратом. Ядро 5×5 почти утроило бы свёрточную часть.
- **Ширина dense** (64) входит дважды: 96·64 + 64 на входе этого слоя и 64·5 + 5 в выходном слое.
- **Число выходов** берётся из реестра свойств. Шестое свойство добавит 64 + 1 = 65 параметров.
- **Размер окна** (64×64) на число параметров не влияет. Веса свёртки не зависят от высоты и ширины картинки, а global average pooling сворачивает любую карту признаков до вектора из 96 чисел. Окно влияет на скорость и память, но не на размер модели.
- **Dropout и L2** число параметров не меняют. Dropout весов не имеет, L2 меняет только loss. Это проверено: с включёнными флагами `countParams()` даёт те же 97 653.

### Как задаём

| Что | Где и как |
|---|---|
| Ширина свёрток и dense | Литералы 16, 16, 32, 32, 64, 96 и 64 в `src/model/arch.ts` (`buildModel`). Чтобы изменить, нужно править код и переобучать модель. |
| Форма входа | `inputShape: [64, 64, 7]` там же. Константы `WINDOW_SIZE = 64` и `CHANNELS = 7` в `src/pipeline/dataset.ts`. Схемы zod (`z.literal(64)`, `z.literal(7)`) не дают собрать датасет или загрузить модель другого формата. |
| Число выходов | Длина `outputOrder` из реестра свойств (`src/registry`). Добавили свойство в реестр — выходов стало больше. |
| Dropout, L2 | Флаги `--dropout` и `--l2` у `npm run train`, по умолчанию 0. На число параметров не влияют. |
| Где число видно | Во время обучения оно не печатается и не попадает в `meta.json`. Тестом не закреплено. Его считали `model.countParams()` при приёмке задач 06 и 005/01 (отчёты в `plans/`). Записано в `docs/03-architecture.md` и `docs/09-results.md`. |

### Как мы пришли к этой ширине

План задачи 06 закладывал вдвое более широкую сеть 32-32-64-64-128-128, это 296 741 параметр. В headless Chromium без видеокарты, на программном рендерере SwiftShader, она стабильно роняла вкладку («Target crashed») через 90–110 секунд обучения. Ни одной эпохи она не проходила. Утечку тензоров и сторожевой таймер Chromium диагностика исключила. Контракт проекта требует, чтобы обучение работало и без видеокарты. Поэтому ширину сузили до 16-16-32-32-64-96, а размер батча уменьшили с 64 до 16.

Позже, в задаче 11, применение модели на cpu-бэкенде заняло 61 мс на окно при бюджете 50 мс. Попробовали сузить сеть ещё сильнее, до 12-12-24-24-48-64 (52 513 параметров). Вариант отменили: применение перевели на wasm-бэкенд, и та же ширина стала работать за 2.6–2.9 мс на окно. Метрики на текущей ширине нас устраивали, поэтому расширять сеть дальше не стали: проблема была в данных, а не в ёмкости модели (`goals.md`).

| Ширина | Параметры | Судьба |
|---|---|---|
| 16-16-32-32-64-96 (текущая) | **97 653** | Обучена, работает в тестах |
| 32-32-64-64-128-128 (исходный план) | 296 741 | ≈ 3× больше. Роняла вкладку под SwiftShader, отказались |
| 12-12-24-24-48-64 | 52 513 | Пробовали ради скорости на cpu-бэкенде, отменили после перехода на wasm |

Ширина менялась в трёх коммитах design-dealer: `b7e0aa8` (сразу 16-…-96), `0bcd3f8` (попытка 12-…-64 и возврат), `0d50afd` (опции dropout и L2 без изменения ширины).

### Где документы расходятся с фактом

- Комментарий в `src/model/arch.ts` округляет число до «~97 600».
- `adr/002-model-input-native-windows.md` до сих пор пишет «порядка 150 тысяч параметров».
- Слайд «Как устроена сеть» и `REPORT.md` говорят, что исходная сеть была «вдвое шире». По каналам это верно, но параметров у неё не вдвое, а втрое больше: 296 741 против 97 653.
- Отчёт задачи 11 оценивает вариант 12-…-64 в «~57k», а по формуле выходит 52 513.

Моё мнение: число параметров стоит закрепить тестом `expect(buildModel(tf, 5).countParams()).toBe(97653)`. Тогда случайная правка ширины не пройдёт незамеченной, а документы будет с чем сверять.
